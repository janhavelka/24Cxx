# EEPROM24Cxx audit, 2026-09-26

The audit reviewed the current checkout against the sixteen standalone I2C
libraries in the sibling Projects directory. Comparison covered public APIs,
transport contracts, state/health/status reporting, cooperative operations,
memory commands, example adapters, CLI parsing/style, packaging and validation.
Sibling repositories were read-only references. No physical board was programmed.

## Findings and fixes

| Finding | Consequence before the change | Resolution |
| --- | --- | --- |
| Unknown transport code trusted a NOT_COMMITTED claim | An invalid adapter result could discard the mandatory programming wait after a possibly accepted write | Only recognized failure codes can establish NOT_COMMITTED; malformed/unknown outcomes preserve uncertainty, wait barrier and no-replay behavior |
| Write/readback evidence was incomplete | An admitted write reported OK before any write; callers could not separately inspect readback status after cancellation/deadline | Pending write status is IN_PROGRESS; verificationAttempted/verifyStatus retain the most recent readback result, including mismatch offset |
| Missing sibling diagnostic API surface | Generic diagnostics needed EEPROM-specific snapshot access | Added state/config/settings aliases, health/error/timestamp getters, memory bounds/chunk getters and public enum names |
| Missing request correlation and owner timeout | A delayed owner cancellation/result action could target newer work; clockless owners could only cancel | Added reserved automatic IDs, explicit owner IDs, qualified poll/cancel/timeout/take, and sibling request names; mismatched actions change no state and perform no I2C |
| Geometry survived teardown while Config reset | Unbound snapshot mixed the previous chip's geometry with the default variant | Reset geometry on end; expose bound and maxAddress explicitly |
| Missing read-only memory CLI tools | Dumps were buffer-limited and lacked ASCII; strings/CRC/text/profile/heap tools were absent | Added cooperative full-range views, escaped text, string scanning across buffers/banks, CRC32, variants/size, heap, verbose and selftest aliases |
| Direct CLI entry accepted control characters | Calls bypassing the character feeder had weaker parsing than terminal input | Both entry paths reject unsupported control/non-ASCII input and oversized lines before mutation |
| CLI configuration/status output hid useful evidence | Staged settings could be confused with active settings; numeric states and limited status text complicated fault analysis | Show staged/active configuration, symbolic transfer/commit states, retained phase statuses, request ID and full health error details |
| ESP-IDF ordinary NACKs collapsed into generic I/O errors | Callers lost typed NACK information; failed reads carried irrelevant write-effect uncertainty | Preserve unspecified NACKs, distinguish address-only probe NACK, and mark read/probe effects NOT_APPLICABLE |
| Wire timeout/buffer contract was incompletely enforced | Callbacks changed timeout persistently and assumed storage/read consumption succeeded | Restore timeout on every return, establish buffer capacity before enabling the adapter, validate arguments, check byte consumption and disable the adapter after buffer invariant violations |
| PlatformIO silently skipped CLI tests | A successful native command covered only core tests | Use standard test_* suite directories and compile the shared CLI in native tests; add a dedicated transport suite |
| Package smoke validation was not reproducible | Release checks depended on a one-off manual export | Add a reusable archive validator and extracted-package CMake build check |
| Current-address chip function was unavailable | Applications could only issue random/sequential addressed reads | Add explicit pure-read transport capability, synchronous/cooperative APIs and pointer tracking; implement both firmware transports |
| Programming could not avoid unchanged chunks | Repeated application updates consumed unnecessary endurance | Compare bounded chunks, skip equal data and retain separate comparison/skip/write/readback evidence |
| Field access required hand-written scheduling and byte codecs | Simple typed persistence duplicated endian conversion and wait handling | Add optional BlockingMemory facade with application wait/clock, typed methods, CRC and page/bank/range helpers |
| CLI lacked comprehensive explicit programming tests | No equivalent scratch suites, mixed tests or typed-layout demos | Add five distinct scratch tests with fixed RAM backup, verified restoration and independent primary/restore evidence; failure/cancellation retains backup for explicit restore |
| Startup and diagnostics were incomplete | Startup did not use tracked initialization; selftest read only a small prefix | Use begin/init presence semantics, print health/help, stream whole configured array in selftest, add watch/page/timing/threshold/stats/assertions |
| WP and interface recovery hooks were absent | Board testing required editing firmware or manipulating GPIO externally | Optional WP starts protected; explicit application-owned bus reset invalidates pointers and imposes a conservative post-STOP wait |
| Raw scans could bypass a cancelled write's barrier | Address probes could run while the physical programming cycle remained pending | Gate scan admission and ticks on the retained core/reset barriers; add cancellation regressions |

Regression tests exercise the actual shared CLI and transport helper code used
by the examples. Core fault tests use an EEPROM model with page wrapping, bank
mapping, write busy periods and WP suppression; these are software evidence.

## Parity decisions

| Area | EEPROM24Cxx contract |
| --- | --- |
| Lifecycle | bind/admission/cancel/timeout/take/end are bus-silent; begin/probe/recover explicitly perform synchronous presence transactions |
| Health | UNINIT/READY/DEGRADED/OFFLINE is passive telemetry; owner I/O remains available offline; known ACK-poll busy NACKs have a separate counter |
| Online/initialization | Match MB85RC's valid-binding semantics, including DEGRADED/OFFLINE; state is the health authority |
| Counters | Per-binding and saturating; bind/end reset them; latest physical error survives a later successful transfer |
| Operations | Read, write, fill, verify, current read and compare-before-write update; verified mutations use separate full-range readback; fixed buffers and retained results |
| Scheduling | One serialized owner; bounded physical callback budget; no hidden tasks, delays, retries, allocation or bus ownership |
| Error taxonomy | Preflight/logical timeout/cancel/content mismatch stay separate from transport NACK/timeout/bus/I/O failures |
| Write evidence | Accepted, programming-completed and readback-verified bytes are separate; neither ACK nor elapsed time proves contents changed |
| CLI | Shared framework-neutral processor, 32-column help, common colors/aliases, strict parsers, cached diagnostics and explicit programming commands |
| Frameworks | C++17 core plus Arduino-ESP32 and native ESP-IDF examples for S2/S3; application controls pins, speed, serialization and recovery |

Sibling APIs differ: for example TCA9548A's isOnline tracks health, whereas
MB85RC's tracks binding. Copying every spelling and behavior indiscriminately
would create contradictions. Existing EEPROM start/poll/take entry points remain
available alongside the added compatibility names.

EEPROM programming starts at STOP and needs page/bank splitting and a persistent
wait barrier, unlike FRAM. FRAM identity, sleep and high-speed commands and sensor
register/reset instructions do not apply to the common EEPROM array. The exact
Zetta chip's documented functions are mapped in the
[chip coverage guide](field-helpers.md), including current-address access and
physical WP/interface-recovery hooks. Current reads require a known pointer and
an explicitly capable transport, preserving ownership discipline.

Comprehensive programming diagnostics require an explicit scratch range and
`confirm`. They consume endurance and temporarily change that range. Fully
successful tests verify restoration; failure/cancellation preserves the RAM
backup and requires explicit `restore confirm`. Power loss cannot preserve a
RAM backup. Ordinary startup, selftest and `stress` remain read-only. Recovery
never automatically replays an uncertain write; the owner can inspect/read back
after the physical barrier settles. See the [CLI reference](../examples/README.md).

## Validation

Actual host, package and four-target firmware results are recorded in
[validation results](validation.md). The separate
[hardware procedure](hardware-validation.md) remains unexecuted: host models and
successful firmware builds do not establish electrical timing, WP behavior,
endurance, retention or power-loss behavior on physical EEPROMs.
